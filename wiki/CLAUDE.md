# Panorama & Oracle Performance – LLM Wiki: Schema & Operating Manual

This file tells the LLM how this wiki is structured and how it is maintained. It
is the configuration that turns a general-purpose chatbot into a **disciplined
wiki keeper**. Read it at the start of every session, before you ingest sources,
answer questions or lint the wiki.

User and LLM evolve this file together. When a convention changes, this file is
adjusted first and the wiki is brought in line afterwards.

The underlying idea (after Andrej Karpathy) is in `LLM-Wiki-Idee.md` (German
translation of his English original — left in German deliberately, see
*Working principles*).

---

## What this wiki is about

- **Subject:** Two closely interlocked halves. First, **Panorama** itself — the
  tool for performance analysis of Oracle databases (Rails on JRuby, shipped as
  `Panorama.jar` and as a Docker image). Second, the **Oracle expertise behind
  it**: how to measure, interpret and improve performance. The two belong
  together — almost every Panorama feature implements an Oracle concept, and
  almost every Oracle concept has a view in Panorama.
- **Purpose:** (a) memory for ongoing development — architectural decisions,
  background of features, known pitfalls, so that nothing has to be derived
  twice; (b) a reference for everyday analysis work; (c) a source pool for
  documentation, talks and answers to users.
- **Audience:** primarily the author of Panorama, occasionally others as well.
  Write so that an experienced DBA without prior Panorama knowledge can follow:
  introduce Panorama-internal terms briefly, assume common Oracle terms.
- **Typical sources:** the author's own talks and slides (as PDF), blog posts and
  technical articles, personal notes, analysis results and records. Oracle
  documentation and whitepapers may be added. For the development half, the
  **Panorama source repository** itself (`raw/panorama-repository.md` points to
  the repository root): a living source — cite file paths and the commit read,
  and expect statements to age with the code.
- **Typical entities:** [[panorama]] and its components (PanoramaConnection,
  Panorama Sampler, the controller domains), Oracle as an organisation and as a
  product, individual Oracle releases, system views (`V$`/`GV$`, `DBA_HIST_*`),
  external tools (SQL Developer, OEM, AWR reports), people and
  conferences/talks.
- **Typical concepts:** [[awr]], [[ash]], wait events, optimizer and
  [[execution-plans]], [[bind-variables-and-cursor-sharing]], I/O and SGA
  metrics, [[management-pack-licensing]], sampling as a technique.

**Where does it belong?** If a page helps someone *analyse a database with
Panorama* — a Panorama feature, a workflow, the Oracle behaviour behind an
evaluation, a recommendation for the analysed system — it goes into `usage/`. If
it describes *how Panorama itself is built* — architecture, internal mechanisms,
reasoned choices in Panorama development — it goes into `development/`.

---

## The three layers

1. **`raw/`** — immutable source documents. The LLM reads them but never edits
   them. They are the authoritative source. Images live in `raw/assets/`.
2. **`wiki/`** — interlinked Markdown generated by the LLM. This layer belongs
   entirely to the LLM: create pages, update them when new sources arrive,
   maintain cross-references, keep everything consistent.
3. **The schema** — this file (`CLAUDE.md`) plus `index.md` and `log.md`.

The user selects sources, steers the analysis and asks questions. The LLM does
the summarising, cross-referencing, filing and bookkeeping.

## Directory structure

```
llm-wiki/
├── CLAUDE.md           # this file – the schema
├── LLM-Wiki-Idee.md    # the underlying idea (Karpathy, German translation)
├── index.md            # catalogue of contents (what exists, each with a one-liner)
├── log.md              # chronological, append-only activity log
├── raw/                # immutable sources (LLM reads, never writes)
│   └── assets/         # images that sources refer to
└── wiki/               # pages owned by the LLM
    ├── overview.md     # top-level synthesis and entry point
    ├── usage/          # how to use Panorama for performance analysis
    ├── development/    # how Panorama works, its architecture and design decisions
    ├── sources/        # one summary per ingested source
    └── syntheses/      # cross-cutting analyses, comparisons, kept answers
```

### Supported source formats

Directly readable: **Markdown/text** (`.md`, `.txt`) and **images**
(`.png`/`.jpg`, in `raw/assets/`).

**PDF** (`.pdf`) — well suited, especially for slide decks. First try reading the
file directly with the Read tool. If that fails (e.g. because the sandbox cannot
find Homebrew's `poppler` on the PATH), proceed like this:
- `pdftotext -layout "raw/file.pdf" -` extracts the text.
- For pages heavy on diagrams or layout:
  `pdftoppm -png -r 110 -f <page> -l <page> "raw/file.pdf" /tmp/out` and then
  **read the generated PNG file** to see the graphic. Clean up `/tmp` afterwards.
- `pdfinfo` gives the page count.

Not directly readable: **`.pptx`**, **`.docx`**, **`.xlsx`** and other Office
formats. Ask the user to export them as PDF (or text/CSV), or convert them during
ingest if a tool is installed (`soffice --headless --convert-to pdf`, or
`python-pptx` for text only). Never try to read a `.pptx` as text. Details are in
`raw/README.md`.

### Where does a page belong?

- **`usage/`** — a *How users use Panorama* page. It describes a Panorama feature, a
  workflow, a technique or a procedure. It should contain an overview page with all menu items and their purpose, and a page for each menu item with the details of its use and the Oracle concepts behind it. 
- **`development/`** — a *How Panorama works* page. It describes Panorama's architecture, design decisions, and internal mechanisms.
- **`sources/`** — the summary of an ingested source. Created on every ingest.
- **`syntheses/`** — an answer, a comparison or an analysis worth keeping. Good
  answers are filed here instead of disappearing into the chat.

The directory says **who the page is for** (user of Panorama or developer of
Panorama). **What kind of page it is** — entity, concept or decision — is
recorded in the front matter field `type`, not in the path. A decision page lives
in the category it is about: a recommendation for the analysed database
(e.g. [[do-not-blanket-index-foreign-keys]]) in `usage/`, a design decision of
Panorama in `development/`. A page that serves both audiences goes where its
main weight lies and links across.

When in doubt, prefer few substantial pages over many thin ones. Split a page
when it covers two clearly separable things.

## Naming conventions

- File names: `kebab-case.md` (e.g. `project-alpha.md`, `agile-estimation.md`).
  File names without diacritics or spaces, so that links and tools stay robust.
- Page title = first line `# H1`, readable (e.g. `# Agile Estimation`).
- Use Obsidian wikilinks for all internal references: `[[project-alpha]]` or
  `[[project-alpha|the Alpha project]]`. Link **with the bare file name only** —
  no directory path, no `.md` (e.g. `[[glossary]]`, never `[[sources/glossary]]`
  or `[[wiki/sources/glossary]]`). The vault root is the repository root; a link
  containing `/` is resolved as a path from the root with no fallback to the file
  name — so partial paths break. All file names are unique, therefore the bare
  form always resolves.
- Source pages: name them after the source and keep the name stable (e.g.
  `2026-04-architecture-concept.md`).

## Page format

Every wiki page starts with YAML front matter (for Obsidian Dataview and
Silverbullet queries). Keys and values in the front matter stay English so that
queries remain stable:

```markdown
---
title: Project Alpha
type: entity            # entity | concept | source | decision | synthesis | overview
subtype: product        # entities only: person | organisation | product | system | component | event | external
status: stub            # stub | draft | maintained
tags: [core]
created: 2026-01-15
updated: 2026-01-15
sources: []             # file names in raw/ the page rests on, e.g. [architecture-concept.pdf]
---

# Project Alpha

One sentence defining what this is.

## Summary
...

## Details
...

## Relationships
- Works together with [[team-beta]]
- Rests on [[agile-estimation]]

## Open questions
- ...

## Sources
- [[2026-04-architecture-concept]]
```

The sections adapt to the page type. Source pages additionally contain
**`## Key points`**, **`## Impact on the wiki`** and a reference to the raw file
in `raw/`.

### Decision pages

Pages with `type: decision` have an **additional mandatory field** in the front
matter:

```yaml
decision_status: proposed   # proposed | adopted | resolved | rejected | superseded
```

- **`proposed`** — on the table, not yet decided. If it is actively contested,
  write "contested" in the text.
- **`adopted`** — a choice has been made and is being implemented.
- **`resolved`** — a contested question has been settled (typically after a
  disagreement between parties had been documented).
- **`rejected`** — the proposal was decided against.
- **`superseded`** — overtaken by a later decision; link the successor page.

Three rules keep decisions honest:

1. **The status field is the single truth.** The one-liner in `index.md`, the
   first paragraph of the page and every other page mentioning the decision must
   match it. Divergences are *status drift* — see check 9 in `wiki-lint`.
2. **Deciding does not mean all objections are settled.** If a decision is taken
   while questions remain open, do not delete them. Move them into a section
   such as `## Open despite the decision (implementation risks)` so they survive
   as implementation risks.
3. **Record the provenance of the decision** — date, forum and the document or
   clarification it rests on. If a decision rests on a statement by the user
   rather than on a source in `raw/`, that must be stated there.

### Claims and evidence

- Every non-obvious claim can be traced to a source. Back it up with a wikilink
  to the source page and, where useful, with the file name in `raw/`.
- If a new source contradicts an existing claim, **do not silently overwrite
  it**. Keep both, mark the older one and record the contradiction under
  `## Open questions` and in the log. Prefer the newer or more authoritative
  source, but preserve the history of the change.
- Separate facts (from a source) from conclusions (the LLM's synthesis). Mark
  conclusions, e.g. `> Conclusion: …`.

## Operations

### Setup (skill: `wiki-setup`)

Once at the beginning: asks for subject, purpose, audience and typical sources,
fills the section "What this wiki is about" and personalises
`wiki/overview.md`, `index.md`, `CONFIG.md` and `README.md`.

### Ingest (skill: `wiki-ingest`)

When the user puts a source into `raw/` and wants it ingested:

1. Read the source completely (the text first, then look at referenced images
   separately).
2. Discuss the key points with the user before changing many pages — unless they
   explicitly ask for batch processing.
3. Create or update a **source page** in `wiki/sources/` with a summary and key
   points.
4. Update or create the affected pages in `wiki/usage/` and
   `wiki/development/` (entities, concepts, decisions). One source
   often touches 5–15 pages. Add and strengthen cross-references.
5. Mark contradictions with existing claims.
6. Update **`index.md`** (add new pages, refresh one-liners).
7. Append an entry to **`log.md`**.
8. Tell the user which pages have changed.

### Query (skill: `wiki-query`)

When the user asks a question:

1. Read `index.md` first to find matching pages, then go deeper. For keywords not
   yet in the index, `grep` across `wiki/`.
2. Formulate an answer with evidence (wikilinks to the pages and sources used).
3. If the answer has lasting value (a comparison, an analysis, a discovered
   connection), offer to file it as a page in `wiki/syntheses/`, so that
   exploration accumulates in the wiki.
4. Write noteworthy questions into the log.

### Lint (skill: `wiki-lint`)

Regular health check. Looks for contradictions between pages, outdated claims
that newer sources have superseded, orphaned pages (no incoming links),
important concepts without their own page, missing cross-references and
knowledge gaps that a source or a web search could close. The result is a report
with proposed corrections; they are applied after approval.

## index.md and log.md

- **`index.md`** is content-oriented: a catalogue of all pages, grouped by
  category, each with a wikilink and a one-liner. Updated on every ingest.
- **`log.md`** is chronological and append-only. Every entry starts with the same
  prefix so it stays findable via `grep`:
  `## [YYYY-MM-DD] <op> | <subject>` with `<op>` ∈
  `setup | ingest | query | lint | maintenance`.
  Example: `grep "^## \[" log.md | tail -5` shows the last five entries.

## Working principles

- **Language: English.** Wiki content is written in English, even when the source
  is in another language. Technical terms, proper names, code and quotations stay
  in the original.
  *Exception:* `LLM-Wiki-Idee.md` is a German translation of Karpathy's English
  original and stays as it is — translating it back would be pointless.
  `README.md` documents the template itself, not the subject matter, and also
  stays German.
- The LLM writes the wiki; the user curates and steers. Do not ask the user to
  write pages themselves.
- Keep the wiki **consistent**: when a page changes, update everything that
  refers to it.
- Link instead of duplicating. One canonical page per thing; others link to it.
- Be honest about uncertainty and gaps — record them under `## Open questions`.
- Convert relative dates into absolute ones (relative to today's date).
- Small, verifiable changes. After every operation, tell the user what changed.
